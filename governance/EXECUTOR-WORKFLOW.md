# Executor Workflow

Этот документ определяет рабочий протокол исполнителя на ВМ.

## 1. Получение задачи

Перед началом работы исполнитель должен:

1. прочитать Task ID и полное описание задачи;
2. изучить указанные файлы Project Memory;
3. проверить актуальное состояние рабочей ветки/репозитория;
4. определить зависимости и потенциальные конфликты;
5. убедиться, что критерии приёмки понятны.

Если задача неоднозначна в критической части, исполнитель не должен заполнять пробелы произвольным архитектурным решением.

## 2. Перед изменением кода

Исполнитель должен понять существующую реализацию, а не проектировать замену только по названию файла или функции.

До написания новой логики необходимо проверить существующую кодовую базу на наличие близких механизмов:

- поиск существующих функций/services/repositories/components;
- поиск повторяющихся бизнес-правил;
- поиск существующих validators/helpers;
- проверка consumers изменяемых контрактов;
- проверка уже используемых библиотек и инфраструктурных механизмов.

Если существующий механизм можно корректно переиспользовать без ухудшения архитектуры, предпочтительно использовать его вместо создания дубликата.

Нельзя удалять существующее поведение без проверки его consumers и требований.

## 3. Реализация

Код должен быть production-grade:

- явные контракты;
- корректная обработка ошибок;
- предсказуемые состояния;
- валидация внешних данных;
- идемпотентность там, где операция может быть повторена;
- транзакционные границы там, где требуется целостность;
- отсутствие скрытых fallback, маскирующих проблемы;
- тесты критических сценариев;
- понятная конфигурация;
- отсутствие секретов в репозитории;
- минимальная достаточная сложность;
- отсутствие dead code;
- отсутствие необоснованного copy-paste;
- использование существующих механизмов там, где это сохраняет корректные границы;
- отсутствие premature abstractions.

### Правило простоты

Не следует усложнять решение ради гипотетических будущих сценариев.

Если две реализации одинаково удовлетворяют требованиям и архитектурным ограничениям, выбирается более простая и локально понятная.

### Правило переиспользования

Перед созданием нового helper/service/component исполнитель обязан убедиться, что аналогичный механизм не существует уже в системе.

Переиспользование не должно быть механическим: если существующий компонент имеет неподходящую ответственность, его нельзя превращать в «god object» ради устранения пары строк duplication.

### Правило dead code

Неиспользуемый код не добавляется «на будущее». После изменения исполнитель должен удалить созданные им неиспользуемые символы, временные debug-конструкции и недостижимые ветви, если они возникли вследствие реализации.

## 4. Изменение Project Memory

Исполнитель может обновлять техническую документацию, если она является непосредственной частью задачи.

Исполнитель не должен самостоятельно переопределять:

- ADR;
- source of truth;
- бизнес-правила;
- ownership данных;
- публичные архитектурные контракты.

Такие изменения предлагаются архитектору.

## 5. Самопроверка

До отчёта исполнитель обязан проверить:

- lint/typecheck, если применимо;
- unit/integration tests;
- миграции;
- сборку;
- критические happy path;
- негативные сценарии;
- отсутствие debug-кода и секретов;
- отсутствие случайных изменений вне области задачи;
- отсутствие очевидного duplication в изменённой области;
- отсутствие неиспользуемых символов/зависимостей, появившихся из-за задачи;
- отсутствие неоправданной сложности в новом control flow;
- что новые абстракции действительно используются и имеют понятную ответственность.

Для существенных изменений рекомендуется выполнять targeted codebase search по существующим аналогам до завершения задачи.

Если проверка невозможна, это должно быть прямо указано в отчёте.

## 6. Commit

Commit должен быть логически целостным и иметь понятное сообщение.

Не следует смешивать реализацию задачи с unrelated refactoring.

Если рефакторинг необходим для корректной реализации задачи, его границы и причина должны быть указаны в отчёте.

## 7. Отчёт

После push исполнитель выполняет два действия:

### 7a. Обновление статуса

Обновить Status в task-файле (`work/active/TASK-XXX.md`) на `IMPLEMENTED`.

### 7b. Durable Executor Report

Создать директорию `work/evidence/TASK-XXX/` и сохранить в ней файл
`EXECUTOR-REPORT.md` по шаблону `work/templates/EXECUTOR-REPORT-TEMPLATE.md`.

Task-файл при этом остаётся в `work/active/` до вердикта архитектора.

Формат отчёта:

```text
# EXECUTOR REPORT — TASK-XXX

Task: TASK-XXX — <task name>
Status: IMPLEMENTED
Date: YYYY-MM-DD

## Commits
- <sha> <message>

## Changed
- <что изменено>

## Verified
- <команда/проверка>

## Code Quality
- Reuse search: ...
- Duplication: ...
- Dead code: ...
- Complexity: ...
- New abstractions: ...

## Not Verified
- <что не удалось проверить>

## Known Risks
- <известные ограничения>

## Memory
- <обновлённые файлы или обоснование>
```

Отчёт не должен утверждать успешность проверки, которая фактически не выполнялась.

### 7c. TASK-REGISTRY

Обновить `work/TASK-REGISTRY.md`: статус задачи → IMPLEMENTED.

## 8. После передачи

После отчёта исполнитель не считает задачу принятой. Окончательный статус
устанавливает архитектор после независимого аудита.

Исполнитель может быть запрошен архитектором для доработки (CHANGES_REQUIRED).
В этом случае исполнитель возвращает задачу в IN_PROGRESS, выполняет доработку,
и повторяет шаги 7a–7c (новый EXECUTOR-REPORT.md заменяет предыдущий, либо
дополняет его с пометкой о revisions).

## 9. Handoff при незавершённой задаче

Если исполнитель не может продолжить работу (недоступность, смена исполнителя),
он должен зафиксировать текущее состояние в task-файле:

```text
## Handoff (IN_PROGRESS)

Date: YYYY-MM-DD

### Completed
- <что сделано>

### Commits
- <sha> <message>

### Remaining
- <что осталось сделать>

### Known Issues
- <известные проблемы>

### Next Step
- <следующий конкретный шаг>
```

Это позволяет новому исполнителю продолжить работу без восстановления контекста из чата.
