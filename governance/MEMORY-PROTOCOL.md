# Project Memory Protocol

## 1. Цель

Project Memory — долговременная модель проекта, доступная архитектору и исполнителю через Git.

Память должна позволять новому участнику восстановить актуальное состояние проекта без чтения всей истории чатов.

## 2. Классификация информации

### FACT

Подтверждённое наблюдение, состояние системы или внешний ответ.

Хранится преимущественно в `facts/`.

### REQUIREMENT

Требование заказчика, договора или согласованного технического задания.

Хранится в `requirements/`.

### DECISION

Принятое решение о поведении или архитектуре.

Хранится в `decisions/` и при необходимости отражается в `architecture/`.

### HYPOTHESIS

Рабочее предположение, которое ещё не подтверждено.

Не должно находиться среди подтверждённых фактов без явной маркировки.

### OPEN QUESTION

Вопрос, от ответа на который зависит дальнейшее решение.

Хранится в `discovery/`.

### LESSON

Устойчивый вывод, который должен влиять на будущую работу.

Хранится в `lessons/`.

## 3. Запись нового знания

При появлении устойчивого знания определить его тип до записи.

Нельзя писать одно и то же утверждение как факт, решение и гипотезу одновременно без явного объяснения разных аспектов.

## 4. Изменение факта

Если подтверждённый факт больше не актуален:

- обновить актуальное описание;
- сохранить причину изменения и источник, если это существенно;
- не оставлять два противоречивых «текущих» факта.

История Git сохраняет предыдущую редакцию.

## 5. Изменение решения

Архитектурное решение не переписывается молча.

Если решение изменилось:

1. создать новое ADR либо явно оформить supersession существующего;
2. указать старое решение;
3. указать причину изменения;
4. описать последствия;
5. обновить зависимые архитектурные документы.

## 6. Source of Truth

Для каждого критического домена должно быть понятно:

- кто владеет данными;
- где находится источник истины;
- какие системы имеют read/write access;
- что является производной копией;
- как обрабатывается рассинхронизация.

Нельзя вводить второй источник истины только потому, что локально так проще реализовать.

## 7. Traceability

По возможности важные утверждения должны быть трассируемы:

`Requirement → Decision → Architecture → Task → Implementation → Audit`

Не каждый технический commit требует отдельного ADR, но критические бизнес-правила и архитектурные инварианты должны иметь обратную связь с памятью проекта.

## 8. Запрет на хранение секретов

Project Memory не должна содержать пароли, API keys, токены, приватные ключи, платёжные секреты или иные credentials.

Персональные данные клиента и иные чувствительные данные хранятся только в необходимом безопасном виде и не должны попадать в Git без явной необходимости и правового основания.

## 9. Синхронизация после работы

После принятия существенной задачи архитектор проверяет Project Memory. Если
реализация изменила знания проекта, память обновляется до перехода к следующему
связанному этапу.

После той же проверки архитектор обязан:

1. Проверить `PROJECT-STATE.md` и обновить его, если изменились проектная фаза,
   состояние реализации, архитектура, важные решения, ограничения, блокеры,
   активная работа, принятые milestones или следующий контролируемый шаг.

2. Проверить `work/TASK-REGISTRY.md` — запись задачи должна быть перенесена
   из Active в Completed.

3. Убедиться, что `work/evidence/TASK-XXX/` содержит все durable artifacts:
   task-файл, EXECUTOR-REPORT.md, ARCHITECT-AUDIT.md.

PROJECT-STATE.md обновляется также при создании новой задачи в статусе READY
(изменение состава активной работы).
