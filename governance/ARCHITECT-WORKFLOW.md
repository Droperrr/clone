# Architect Workflow

Этот документ определяет практический цикл работы архитектора проекта.

## 1. Перед ответом по проекту

Если вопрос затрагивает проект, архитектор сначала определяет, какой Project Memory нужен для ответа. Для существенных вопросов проверяются как минимум:

- `README.md`;
- релевантные `facts/`;
- релевантные `requirements/`;
- релевантные `architecture/`;
- релевантные `decisions/`;
- `discovery/open-questions.md`, если есть неопределённость;
- актуальные task/work документы, если вопрос относится к работе исполнителя.

Не требуется перечитывать весь репозиторий на каждый вопрос, но нельзя делать архитектурные выводы на основании только текущего сообщения чата, если нужная информация уже должна находиться в Project Memory.

## 2. Постановка задачи исполнителю

Каждая существенная задача должна содержать:

- Task ID;
- цель;
- контекст;
- входные требования;
- ограничения;
- область изменений;
- что не входит в задачу;
- критерии приёмки;
- обязательные проверки/тесты;
- ожидаемые изменения Project Memory;
- зависимости и блокеры.

Для задач, изменяющих код, критерии должны включать не только функциональность, но и требование сохранить качество существующей кодовой базы: отсутствие необоснованного duplication, dead code и излишней сложности.

Задача должна быть проверяема без интерпретации скрытых ожиданий.

## 3. Контроль границ

Архитектор не должен поручать исполнителю «сделать как-нибудь». Если существует несколько допустимых вариантов, архитектор либо выбирает вариант, либо поручает исследовательскую задачу с явными критериями выбора.

Если во время реализации обнаруживается архитектурная развилка, исполнитель не должен выбирать долгосрочное решение молча.

## 4. Приёмка

После отчёта исполнителя архитектор рассматривает его как заявление, которое нужно проверить.

Архитектор переводит задачу в статус AUDIT (обновляет Status в task-файле) при начале проверки.

Порядок:

1. найти commits;
2. проверить diff;
3. прочитать затронутый код целиком в достаточном контексте;
4. сопоставить реализацию с требованиями;
5. проверить архитектурные инварианты;
6. проверить существующие похожие реализации и возможное дублирование;
7. проверить сложность нового решения и возможность безопасного упрощения;
8. проверить dead/unreachable code и неиспользуемые зависимости;
9. проверить негативные сценарии и failure modes;
10. проверить тесты;
11. проверить побочные изменения;
12. проверить документацию и Project Memory;
13. сформировать verdict.

Архитектор не должен ограничиваться вопросом «работает ли новый код». Нужно проверить, **стал ли код лучше интегрирован в систему после изменения**.

## 5. Verdict

Допустимы только следующие результаты:

### ACCEPTED

Работа соответствует задаче и архитектуре, не создаёт необоснованного структурного
ухудшения кодовой базы. Можно двигаться дальше.

Действия архитектора:
1. Создать `work/evidence/TASK-XXX/ARCHITECT-AUDIT.md` по шаблону
   `work/templates/ARCHITECT-AUDIT-TEMPLATE.md`.
2. Переместить task-файл из `work/active/` в `work/evidence/TASK-XXX/`.
3. Обновить `work/TASK-REGISTRY.md` — перенести запись из Active в Completed.
4. Проверить `PROJECT-STATE.md` — обновить Work State, Next Step, milestone при необходимости.
5. Проверить Project Memory — зафиксировать новые FACT/DECISION/LESSON, если появились.

### CHANGES_REQUIRED

Есть конкретные дефекты или архитектурные/quality нарушения. Архитектор перечисляет
их по приоритету и возвращает задачу исполнителю.

Действия архитектора:
1. Создать `work/evidence/TASK-XXX/ARCHITECT-AUDIT.md` с findings.
2. Обновить Status в task-файле → CHANGES_REQUIRED (файл остаётся в `work/active/`).
3. Обновить `work/TASK-REGISTRY.md`.

### BLOCKED

Корректная реализация невозможна без внешнего решения, доступа или подтверждения.

Действия: обновить Status в task-файле с указанием причины блокировки.

### REJECTED

Предложенный подход фундаментально несовместим с архитектурой или требованиями.

Действия архитектора:
1. Создать `work/evidence/TASK-XXX/ARCHITECT-AUDIT.md` с rationale.
2. Переместить task-файл из `work/active/` в `work/evidence/TASK-XXX/`.
3. Обновить `work/TASK-REGISTRY.md`.
4. Проверить `PROJECT-STATE.md`.

## 6. Аудит должен быть независимым

Нельзя ограничиваться проверкой перечисленных исполнителем файлов. Нужно искать:

- неучтённые зависимости;
- дублирование логики;
- нарушение ownership/source-of-truth;
- race conditions;
- неидемпотентные операции;
- невалидные состояния;
- проблемы миграций;
- утечки данных;
- небезопасные default values;
- отсутствующие rollback/failure paths;
- регрессии существующих сценариев;
- dead/unreachable code;
- неиспользуемые зависимости и символы;
- чрезмерную вложенность и сложность;
- неоправданные абстракции;
- copy-paste решения;
- нарушение cohesion/coupling boundaries;
- появление технического долга.

При необходимости архитектор должен выполнить поиск по кодовой базе, а не делать вывод об отсутствии дублирования только по изменённому файлу.

## 7. После принятия

Если реализация изменила понимание проекта, архитектор обязан обновить соответствующий Project Memory. Не следует полагаться на память чата как на долговременное хранилище.

Если во время аудита обнаружено качество-критичное системное правило, которое должно применяться дальше, оно должно быть перенесено в соответствующий governance/lesson документ.

## 8. Коммуникация

Отчёт архитектора исполнителю должен быть конкретным: что проверено, что принято, что не принято, почему и что именно нужно изменить. Формулировки «переделай лучше» без проверяемого результата недопустимы.
