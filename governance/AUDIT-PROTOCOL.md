# Audit Protocol

## 1. Назначение

Аудит — независимая проверка результата исполнителя. Его задача — установить не «есть ли изменения», а «соответствуют ли изменения задаче, архитектуре, качеству кода и production требованиям».

Аудит обязан проверять результат как часть коммерческой системы, а не как изолированный фрагмент кода.

## 2. Audit levels

### L1 — Task correctness

Проверить критерии приёмки и непосредственное поведение.

### L2 — Architectural correctness

Проверить ownership, source of truth, boundaries, contracts, dependencies и соответствие ADR.

### L3 — Production correctness

Проверить безопасность, целостность данных, concurrency, idempotency, observability, error handling, migration/deployment impact и эксплуатационные риски.

### L4 — Codebase quality

Проверить, что новая реализация улучшает или как минимум не ухудшает структурное качество кодовой базы:

- дублирование кода и логики;
- дублирование бизнес-правил;
- мёртвый и недостижимый код;
- неиспользуемые функции, классы, параметры, зависимости и конфигурацию;
- излишнюю сложность алгоритмов и control flow;
- чрезмерную вложенность;
- неоправданные абстракции и premature generalization;
- слишком большие функции/классы/модули;
- слабую cohesion и чрезмерный coupling;
- нарушение существующих границ модулей;
- повторное изобретение уже существующего механизма;
- неиспользуемые или дублирующие зависимости;
- неочевидные side effects;
- ухудшение читаемости и локальной понятности;
- нарушение naming и единообразия существующих conventions;
- copy-paste реализацию там, где нужен общий механизм;
- новый технический долг, не зафиксированный явно.

Для любой новой нетривиальной логики архитектор должен задать вопрос: **«Существует ли уже в системе механизм, который решает эту задачу или близкую задачу?»**

Нельзя считать задачу качественно выполненной только потому, что новый код функционально работает.

## 3. Обязательность уровней

Для любой задачи, изменяющей код, обязательны L1, L2 и L4.

L3 обязателен, если затронуты данные, внешние интеграции, авторизация, платежи, персональные данные, concurrency, deployment или иные эксплуатационно критичные области.

Для архитектурных, интеграционных и security-critical задач все четыре уровня обязательны.

## 4. Evidence

Аудит должен опираться на наблюдаемые evidence:

- diff;
- исходный код;
- связанные существующие реализации;
- тесты;
- результаты команд;
- схемы/миграции;
- конфигурацию;
- документацию;
- состояние внешних контрактов, если оно доступно;
- результаты поиска по кодовой базе, если требуется проверить дублирование или использование.

Сообщение исполнителя является вспомогательным источником контекста, а не evidence корректности.

## 5. Обязательные вопросы

### Functional

- реализован ли заявленный сценарий;
- соблюдены ли acceptance criteria;
- обработаны ли ошибки;
- что происходит при повторе операции;
- что происходит при частичном отказе.

### Architecture

- не создан ли второй source of truth;
- не нарушен ли ownership;
- не появились ли скрытые coupling/dependencies;
- соответствует ли реализация ADR;
- не изменились ли контракты consumers;
- не дублирует ли новая реализация существующий архитектурный механизм.

### Code quality

- существует ли уже код, который можно безопасно переиспользовать;
- не продублирована ли существующая логика;
- нет ли dead/unreachable code;
- нет ли новых неиспользуемых символов или зависимостей;
- можно ли упростить control flow без потери корректности;
- нет ли лишней вложенности;
- оправдана ли каждая новая абстракция;
- не создан ли generic framework там, где нужен один конкретный use case;
- не стал ли модуль слишком связанным с другими модулями;
- сохраняется ли cohesion;
- понятны ли названия и ответственность компонентов;
- не спрятаны ли side effects в неожиданных местах;
- не появился ли технический долг, который необходимо зафиксировать.

**Правило минимальной достаточной сложности:** среди решений, удовлетворяющих требованиям и архитектурным ограничениям, предпочтительно самое простое решение, которое остаётся расширяемым там, где расширяемость действительно нужна.

**Правило reuse-before-duplication:** перед добавлением новой логики необходимо проверить существующие helpers/services/repositories/components и использовать их, если это не ухудшает архитектуру.

**Правило no-dead-code:** новый код, который не нужен для текущего поведения, не должен оставаться «на будущее» без явной причины.

### Data integrity

- транзакционные границы;
- уникальность;
- consistency;
- race conditions;
- idempotency;
- rollback.

### Security

- authentication/authorization;
- input validation;
- sensitive data;
- secrets;
- access boundaries;
- logging of sensitive values.

### Operations

- конфигурация;
- миграции;
- health/readiness;
- logs/metrics;
- failure recovery;
- deployment compatibility.

### Maintainability

- читаемость;
- тестируемость;
- отсутствие необоснованной сложности;
- отсутствие временных workaround без фиксации технического долга;
- соответствие существующим conventions;
- отсутствие локальных решений, которые усложняют дальнейшее развитие системы.

## 6. Findings

Каждое существенное замечание должно иметь:

- severity;
- место в коде/документации;
- описание проблемы;
- почему это важно;
- ожидаемое исправление или критерий результата.

Severity:

- **CRITICAL** — блокирует приёмку, возможна потеря данных, нарушение безопасности или фундаментальная архитектурная ошибка;
- **HIGH** — существенная функциональная/архитектурная проблема либо значимое структурное ухудшение кодовой базы;
- **MEDIUM** — важный дефект качества, надёжности или поддерживаемости;
- **LOW** — не блокирует приёмку, но улучшение желательно.

Не каждое совпадение кода является дефектом: дублирование допускается, если оно сознательно сохраняет правильные границы и устранение duplication создало бы худшую связанность. В таком случае архитектор должен зафиксировать rationale.

## 7. Verdict

`ACCEPTED` допускается при отсутствии CRITICAL/HIGH проблем и выполнении критериев задачи.

Наличие MEDIUM/LOW замечаний не должно автоматически блокировать приёмку, если они не нарушают обязательные критерии и не создают скрытый существенный технический долг. Существенные остаточные замечания должны быть зафиксированы.

`CHANGES_REQUIRED` — если есть блокирующие или существенные замечания.

`BLOCKED` — если корректный verdict невозможен из-за отсутствующего внешнего evidence.

`REJECTED` — если подход фундаментально несовместим с архитектурой или требованиями.

## 8. Audit record

Для существенных задач результат аудита фиксируется как durable artifact:
`work/evidence/TASK-XXX/ARCHITECT-AUDIT.md` (шаблон: `work/templates/ARCHITECT-AUDIT-TEMPLATE.md`).

Краткий формат для task-файла:

```text
AUDIT: TASK-XXX
COMMIT(S): <sha>
VERDICT: ACCEPTED | CHANGES_REQUIRED | BLOCKED | REJECTED

CHECKED:
- Functional correctness
- Architecture
- Code quality
- Production concerns, if applicable

FINDINGS:
- [SEVERITY] ...

CODE QUALITY:
- Duplication: ...
- Dead code: ...
- Complexity: ...
- Abstractions/coupling: ...
- Technical debt: ...

MEMORY UPDATED:
- ...
```
